# E2E 테스트 (Playwright)

## 범위

앱 전체를 다 덮을 수 없어서, 커밋 활동량이 가장 많고(`funding-history` 41회, `entities/project` 35회,
`buyer-refunds` 23회, `order-checkout` 22회 — 최근 100커밋 기준) 실제 라이브 방송·결제 게이트웨이
같은 외부 서비스 없이 끝까지 자동화 가능한 여정만 고른다. 스펙은 IA 문서(`6팀_IA_v1.3.xlsx`)의
UCS(유저 플로우)·예외케이스 시트 단계 번호와 대응시켜 둔다:

IA와 실제 화면이 다른 곳(스펙은 **현재 화면 동작** 기준이다):

- 예외 소비자 25는 IA에 "아직 참여한 프로젝트가 없어요" + 둘러보기 CTA가 있지만 화면은 "참여 내역이 없습니다."만 보여 준다.
- 예외 소비자 34("LIVE 검증 정보를 정리하고 있어요" 생성 중 안내)는 화면에 없다. 검증 정보가 없으면 "등록된 검증 정보가 없습니다."가 나온다.
- 판매자 1("홈 화면에서 판매자 전환")에 해당하는 버튼이 화면에 없다. 스펙은 `/seller/projects`로 바로 진입한다.
- 예외 판매자 10은 IA가 "누락 항목 안내 문구·강조"인데 화면은 저장 버튼을 비활성화한다(임시저장만 안내 문구를 띄운다).
- 로그인 화면의 "비밀번호를 입력해주세요." 안내는 비밀번호가 비면 버튼이 비활성이고 Enter 제출도 막혀 UI에서 볼 수 없는 것으로 보인다(브라우저 동작에 의한 추정). `auth-guard`는 버튼 비활성과 요청 없음만 검증한다.
- 관심 목록은 IA에 찜을 추가하는 경로가 없지만, 프로젝트 상세의 "프로젝트 찜" 버튼이 #448부터 찜 API에 연결돼 있어 목록 밖에서도 상태가 바뀐다.

제외한 것과 이유:

- **실제 Toss 결제 위젯** — `/payment/[orderId]`은 버튼 클릭이 아니라 진입 즉시
  `NEXT_PUBLIC_TOSS_CLIENT_KEY`가 있으면 실제 Toss 스크립트를 로드한다. `playwright.config.ts`의
  `webServer.env`가 이 키를 항상 빈 문자열로 덮어써서, 로컬 `.env.local`에 실제(테스트) 키를 넣어
  둬도 E2E 실행 시엔 "결제 환경이 설정되지 않아 결제를 진행할 수 없습니다" 상태로 안전하게
  멈춘다 — 구매 퍼널 테스트의 최종 단언이 이 문구다.
- **실제 라이브 영상 스트림·AI 생성**(스토리·큐시트) — 서버 인프라 자체가 필요해 E2E로 검증할
  수 없다.
- **실제 SMS·PortOne 본인인증** — MSW 목업 경계 밖. `buyer-signup`은 인증을 검증하지 않는다. 개발 서버 + MSW에서
  인증창 없이 성공을 돌려주는 어댑터 경로(`portone-identity-adapter.ts`)를 타고, 그 뒤의 화면·입력 검증·가입 요청만 본다.
  본인인증이 끼는 아이디·비밀번호 찾기(`/auth/recovery/*`)도 다루지 않는다.
- **소비자 LIVE 시청·판매자 LIVE 송출/큐시트** — 영상·실시간 채팅이 필요해 다루지 않는다.
- **프로젝트 상세의 찜 버튼**(#448) — 목업(`src/mocks/discovery-handlers.ts`)은 공개 UUID 찜 경로까지
  덮지만 스펙은 아직 없다. `buyer-wishlist`는 관심 목록의 해제·되돌리기까지만 검증한다. 상세 하트의
  네 갈래(조회 실패·서버 값·요청 중·데모)는 `buyer-project-detail.test.mjs`가 렌더로 잠근다.

## 실행

```
pnpm test:e2e              # 헤드리스, 전체 순차 실행
pnpm exec playwright test --ui       # UI 모드 — 테스트별로 재생하며 브라우저·타임라인을 직접 본다
pnpm exec playwright test --headed   # 브라우저 창을 띄운 채 순서대로 실행
```

`playwright.config.ts`가 `pnpm dev`를 `NEXT_PUBLIC_MSW_ENABLED=true`·빈 Toss 키로 직접 띄우므로 dev 서버를
미리 띄워 둘 필요는 없다. `reuseExistingServer`는 꺼 두었다 — 이미 떠 있는 서버(`pnpm dev` 등)는 이 env가
적용돼 있지 않아 실제 BE·Toss로 나갈 수 있어서, 재사용하지 않고 3000번 포트가 사용 중이면 실행을 멈춘다.
테스트 전에 그 서버를 먼저 종료한다(`pkill -f "next dev"`).

`webServer.env`는 API 프록시(`API_PROXY_TARGET`)도 빈 문자열로 덮어쓴다. `.env.local`에 프록시가 있으면
목업 없는 `/api` 요청이 실제 dev BE로 나가 결과가 dev 데이터에 따라 달라졌다(#510). 이제 목업 없는 요청은
e2e 서버에서 404로 끝나므로, 스펙이 새 엔드포인트를 지나면 아래 MSW 핸들러를 먼저 추가한다.

**주의**: `--ui` 모드로 한참 조작한 뒤처럼 dev 서버를 오래 띄워 둔 채 다시 돌리면 컴파일 캐시나 MSW 인메모리
상태가 누적돼 로그인 단계부터 실패하는 등 불안정해질 수 있다. 이상하게 실패하면 서버를 죽이고 재시도한다.

## 왜 백엔드 없이 돌아가는가 — MSW

이 저장소는 실제 BE 없이 프론트만 존재한다. `src/mocks/*.ts`가 `msw`(v2, 기존 devDependency)로
E2E가 지나는 모든 REST 경로를 흉내 낸다:

- `fixtures.ts` — 스펙과 핸들러가 공유하는 고정 UUID(프로젝트·주문·판매자 프로젝트·리워드)와 로그인 픽스처.
- `auth-handlers.ts` — 약관·이메일 중복 확인·본인인증 결과·회원가입·로그인·토큰 갱신·내 정보.
- `project-handlers.ts` — 공개 프로젝트/리워드 조회, LIVE 체크 탭, 판매자 프로젝트 목록·건수·생성·기본정보·리워드 생성. 재고가 없는 한정 리워드(`FIXTURE_LIMITED_REWARD_ID`, 주문 시 `INSUFFICIENT_STOCK`)와 품절 리워드도 둔다. 이 리워드들은 구매 퍼널 스펙이 고르는 "기본 무드등 1개"와 무관하다.
- `order-handlers.ts` — 주소·쿠폰·주문 미리보기/생성/조회/취소, 결제 시도·승인(`pgOrderId`는 `pg-<주문 UUID>`). **주문 인메모리 스토어를
  export**해서 `refund-handlers.ts`가 같은 데이터를 본다 — 그래야 "취소 신청 → `/my/refunds`에
  반영"이 실제로 성립한다(전엔 이 둘이 분리된 목업이라 반영이 안 됐던 버그를 여기서 고쳤다).
- `refund-handlers.ts` — 환불 추정·환불 목록(위 스토어의 취소·반품·교환 건을 매핑), 반품·교환·하자 신청.
- `discovery-handlers.ts` — 통합 검색(프로젝트·판매자)·최근/인기 검색어·찜·팔로우. 로그인한 요청의 검색어만 최근 검색어에 남는다(BE와 같다).
- `live-handlers.ts` — 프로젝트별 종료된 LIVE·공개 숏 클립 목록(상품 상세 LIVE 체크 탭). 기본 프로젝트에는 종료 LIVE·시연 클립이 한 건씩 있어 LIVE 체크 탭이 보인다(#461·#510). `projectId` 없는 LIVE 조회(LIVE 메인 등)는 목업이 없다.
- `fulfillment-handlers.ts` — 판매자 제작·배송 트래커(단계 전환·기록·일정 변경)와 발송정보(주문 목록·송장), 구매자 배송 현황. `FIXTURE_SELLER_PROJECT_ID` 하나만 다루며 상태는 `sessionStorage`에 미러링해 판매자·구매자 화면 사이를 하드 네비게이션으로 오가도 이어진다.

인메모리 스토어는 `page.goto` 같은 하드 네비게이션마다 새 JS 컨텍스트로 초기화돼 사라진다. 그래서 하드 네비게이션을
넘어 이어져야 하는 상태만 `sessionStorage`에 미러링한다 — **주문 스토어**(`order-handlers.ts`)와 **제작·배송 상태**
(`fulfillment-handlers.ts`)가 그렇다. 나머지(판매자 새 프로젝트, 검색어·찜·팔로우 등)는 메모리에만 있어서 스펙이
하드 네비게이션 없이 같은 탭 안에서 흐름을 끝내야 한다. 테스트 간 리셋은 하지 않는다 — 스펙마다 새 브라우저
컨텍스트라 각자 새 상태로 시작한다.

스펙이 기본 픽스처와 다른 주문 상태(참여 0건, 배송 완료 등)가 필요하면 `e2e/support/orders.ts`의
`seedOrders`로 앱이 뜨기 전에 `sessionStorage`를 채운다(키가 있으면 기본 픽스처를 넣지 않는다).

## 인증

`e2e/support/login.ts`의 `loginAsFixtureUser(page)`가 실제 로그인 폼을 조작해 세션을 만든다(로그인이
필요한 스펙 대부분이 공유한다. 로그인 자체를 검증하는 `auth-guard`만 폼을 직접 조작한다). 이 저장소엔 `middleware.ts`가 없고 인증은
전적으로 클라이언트 상태라, 서버 리다이렉트를 가정한 우회는 불가능하다.

`auth-handlers.ts`의 토큰 갱신(`token/refresh`)은 `refreshToken` 쿠키가 있는지만 보고 값은 검사하지 않는다.
로그인 응답이 이 쿠키를 심으므로, 로그인한 뒤 `page.goto`로 하드 네비게이션해도 세션이 복구된다.

## 확장할 때

- 새 화면/엔드포인트가 필요하면 해당 MSW 핸들러 파일에 추가하고, `src/mocks/handlers.ts`에
  배선한다.
- 셀렉터는 `getByRole`/`getByLabel`/`getByText` 우선 — 이 저장소엔 `data-testid`가 없고, 실제
  컴포넌트 JSX를 먼저 읽고 문자열을 확정한다(추측 금지, 실행해서 확인).
- `playwright.config.ts`의 `workers: 1`은 의도적이다(`next dev`가 라우트별 최초 컴파일을 동시
  요청에서 서로 블록해 병렬 워커가 불안정했다). 스펙 17개(테스트 46개)를 순차로 돌려 1분 안팎이다.
