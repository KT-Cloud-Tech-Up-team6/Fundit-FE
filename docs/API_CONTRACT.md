# API 계약 초안

작성일은 2026-09-07이며, 상태는 FE·BE 검토용 초안이다.

## 1. 목적과 근거

FE·BE 연동에 필요한 공통 규칙, 인증·회원 및 프로젝트 계약과 남은 확인 사항을 정리한다. 근거는 전달받은 다음 자료이며, 백엔드 코드나 실제 서버 응답을 직접 검증한 문서는 아니다.

- API 버저닝·표준 에러 형식 정의서.
- 인증/회원 담당자의 답변.
- 프로젝트 담당자의 답변.
- FE가 전달한 API 계약 질문 목록.

문서에서 사용하는 상태는 다음과 같다.

| 상태           | 의미                                                                                  |
| -------------- | ------------------------------------------------------------------------------------- |
| 정의서 기준    | 전달받은 공통 정의서에 명시된 규칙. 실제 엔드포인트 적용 여부는 별도 검증이 필요하다. |
| 구현 답변 기준 | BE가 설명한 현재 구현. 최종 정책 확정 또는 배포·연동 가능 여부까지 의미하지 않는다.   |
| 미구현         | BE가 미구현이라고 답변한 항목.                                                        |
| 확인 필요      | 답변이 없거나 세부 계약·최종 합의가 필요한 항목.                                      |

이 문서가 Swagger/OpenAPI 또는 BE DTO보다 우선하는 최종 기준인지는 미정이다. 기존 [미확정 정책 문서](./OPEN_DECISIONS.md)의 API 관련 항목을 구체화한 초안이며, 그 밖의 제품 정책은 다루지 않는다.

## 2. 환경과 경로

| 항목                      | 계약 또는 현재 상태                                        | 근거 상태      |
| ------------------------- | ---------------------------------------------------------- | -------------- |
| 개발 API Base URL         | 확인 필요.                                                 | 확인 필요      |
| 운영 API Base URL         | 확인 필요.                                                 | 확인 필요      |
| API 버전 방식             | URL 경로 버전인 `/api/v1/...`을 사용한다.                  | 정의서 기준    |
| 인증 경로                 | 전달된 본인인증 및 회원가입 경로는 `/api/v1/auth/...`이다. | 구현 답변 기준 |
| 프로젝트 경로             | `/api/v1/projects/**`로 통일되는지 답변이 필요하다.        | 확인 필요      |
| 실제 연동 가능한 API 목록 | 환경별 배포 여부와 접근 가능한 명세가 필요하다.            | 확인 필요      |

필드 추가만으로는 버전을 올리지 않으며, 클라이언트는 모르는 필드를 무시한다. 필드 삭제·이름 변경·타입 변경 등 브레이킹 체인지가 발생하면 `/api/v2/...`로 신규 버전을 병행 운영한다.

구버전은 최소 유지 기간을 거친 뒤 종료 공지 후 폐기한다. 최소 유지 기간은 팀 협의 후 확정한다.

## 3. 공통 응답

### 3.1. 성공 응답

정의서 기준으로 도메인 DTO를 HTTP 상태 코드와 함께 별도 래퍼 없이 직접 반환한다. `data`, `code`, `message` 등의 성공 응답 공통 래퍼를 추가하지 않는다.

다음은 정의서의 형식 예시이며, 특정 회원·프로젝트 API의 완전한 DTO를 확정하는 예시는 아니다.

200 OK 단일 객체 예시.

```json
{
  "memberId": 1,
  "nickname": "테스트",
  "email": "user@example.com"
}
```

200 OK 배열 예시.

```json
[
  { "productId": 1, "name": "세상에 없는 프라이팬" },
  { "productId": 2, "name": "세상에 있는 프라이팬" }
]
```

200 OK 페이지네이션 예시.

```json
{
  "content": [
    { "productId": 1, "name": "세상에 없는 프라이팬" },
    { "productId": 2, "name": "세상에 있는 프라이팬" }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 134,
  "totalPages": 7,
  "hasNext": true
}
```

204 응답은 본문이 없다. 201 응답의 본문과 주요 상태별 실제 응답 예시는 추가 공유가 필요하다.

### 3.2. 오류 응답

정의서에서 제공한 표준 오류 응답 예시.

```json
{
  "code": "PAID_ALREADY",
  "message": "결제되었습니다.",
  "detail": null
}
```

| 필드      | 제공된 내용                 | 추가 확인 사항                                |
| --------- | --------------------------- | --------------------------------------------- |
| `code`    | 문자열 오류 코드.           | 도메인별 추가 코드 목록.                      |
| `message` | 문자열 메시지.              | 엔드포인트별 실제 메시지.                     |
| `detail`  | 예시에서 `null`을 반환한다. | 값이 있는 경우의 타입·구조 및 필수 포함 여부. |

`fieldErrors`, `timestamp`, `traceId`는 제공된 표준 형식에 정의되어 있지 않다. 필드별 유효성 오류를 `detail`로 전달하는지 여부도 확인이 필요하다. 예시의 `PAID_ALREADY`에 대응하는 HTTP 상태는 전달되지 않았다.

### 3.3. HTTP 상태와 공통 오류 코드

| HTTP | 의미                          | 공통 오류 코드와 설명                                                  |
| ---- | ----------------------------- | ---------------------------------------------------------------------- |
| 200  | 성공                          | 해당 없음.                                                             |
| 201  | 리소스 생성 성공              | 해당 없음.                                                             |
| 204  | 성공, 응답 본문 없음          | 해당 없음.                                                             |
| 400  | 요청 파라미터·바디 오류       | `INVALID_INPUT`. Body 누락·JSON 형식 오류를 포함한 입력값 유효성 오류. |
| 401  | 인증 실패                     | `UNAUTHORIZED`. 인증 필요.                                             |
| 401  | Access Token 만료             | `TOKEN_EXPIRED`.                                                       |
| 401  | Access Token 유효성 검증 실패 | `TOKEN_INVALID`.                                                       |
| 403  | 권한 없음                     | `FORBIDDEN`.                                                           |
| 404  | 리소스 없음                   | `NOT_FOUND`.                                                           |
| 405  | 지원하지 않는 HTTP 메소드     | `METHOD_NOT_ALLOWED`.                                                  |
| 409  | 충돌·중복                     | `CONFLICT`.                                                            |
| 410  | 리소스 만료                   | `RESOURCE_EXPIRED`. 주문 만료 등.                                      |
| 422  | 비즈니스 규칙 위반            | `BUSINESS_RULE_VIOLATION`.                                             |
| 423  | 리소스 잠김                   | `RESOURCE_LOCKED`.                                                     |
| 429  | 요청 한도 초과                | `TOO_MANY_REQUESTS`.                                                   |
| 500  | 서버 내부 오류                | `INTERNAL_ERROR`.                                                      |
| 503  | 서비스 일시적 사용 불가       | `SERVICE_UNAVAILABLE`.                                                 |
| 503  | 외부 서비스 호출 실패         | `DEPENDENCY_FAILURE`. Auth, Redis 등 의존 서비스 실패.                 |

각 서비스는 공통 코드 외에 도메인 전용 오류 코드를 추가할 수 있다. 본인인증 답변에서는 인증 실패에도 `TOKEN_INVALID`를 사용한다고 명시했다. 공통 정의서의 Access Token 설명보다 사용 범위가 넓으므로 FE 오류 처리 시 해당 엔드포인트의 의미를 함께 확인해야 한다.

### 3.4. 공통 값 표현

| 항목      | 현재 확인된 내용                                        | 남은 확인 사항                                      |
| --------- | ------------------------------------------------------- | --------------------------------------------------- |
| 날짜·시간 | 본인인증 `expiresAt` 예시는 `2026-09-03T12:34:56Z`이다. | 전체 API의 ISO 8601 적용 여부, 기준 타임존, 정밀도. |
| ID        | 공통 성공 예시의 ID는 숫자다.                           | 실제 ID의 숫자·문자열 타입 및 범위.                 |
| 금액      | 전달된 규칙 없음.                                       | 타입, 통화, 단위, 소수점 처리.                      |
| `null`    | 오류 예시의 `detail`은 `null`이다.                      | 다른 필드의 `null` 허용 여부와 필드 생략의 구분.    |

개별 예시만으로 전체 API의 공통 타입을 확정하지 않는다.

## 4. 인증 및 회원가입

### 4.1. Access Token 전달

구현 답변 기준으로 다음 헤더를 사용한다. `JwtAuthenticationFilter`는 이 헤더와 프리픽스만 파싱한다.

```http
Authorization: Bearer <token>
```

### 4.2. CORS와 Refresh Token 쿠키

CORS 및 Credential 설정은 미구현이다. 아래 항목을 결정해야 Refresh Token 쿠키 계약을 확정할 수 있다.

| 확인 항목                 | 필요한 정보                                                                    |
| ------------------------- | ------------------------------------------------------------------------------ |
| 호출 구조                 | 브라우저의 auth-service 직접 호출 또는 FE BFF 경유 여부.                       |
| 직접 호출 시              | 개발·운영 FE Origin의 정확한 URL.                                              |
| BFF 경유 시               | 브라우저가 실제로 보는 Origin과 BFF의 `Set-Cookie` 응답 헤더 릴레이 가능 여부. |
| 쿠키·Credential 세부 계약 | 쿠키 `Domain`, `SameSite`, `Secure` 및 Credential 설정.                        |

### 4.3. 로그인

`LoginSuccessHandler`는 구현 답변 기준으로 다음 두 필드만 반환한다. 값은 형식 설명용 예시다.

```json
{
  "accessToken": "string",
  "mustChangePassword": false
}
```

닉네임 등 회원정보는 로그인 응답에서 의도적으로 제외했다. 별도 `/members/me` API의 존재, 정확한 경로·메소드·응답 및 로그인 엔드포인트의 전체 계약은 확인이 필요하다.

회의에서는 임시 비밀번호 전송 방식에서 즉시 비밀번호 변경 방식으로 변경하기로 했으나, 요구사항 정의서에는 반영되지 않았다는 답변이 있다. 최종 비밀번호 변경 흐름과 `mustChangePassword`의 처리 조건은 확인이 필요하다.

### 4.4. 포트원 본인인증 재검증

FE는 PortOne SDK의 인증 완료 결과에서 받은 `identityVerificationId` 하나를 BE에 전달한다.

```http
POST /api/v1/auth/identity-verifications
```

요청은 `IdentityVerificationRequest` 기준이다.

```json
{
  "identityVerificationId": "string"
}
```

응답은 `IdentityVerificationResponse` 기준이다. 아래 만료 시각은 전달받은 예시다.

```json
{
  "verificationToken": "string",
  "expiresAt": "2026-09-03T12:34:56Z"
}
```

| 결과              | HTTP      | 오류 코드            |
| ----------------- | --------- | -------------------- |
| 성공              | 확인 필요 | 해당 없음.           |
| 인증 실패         | 401       | `TOKEN_INVALID`      |
| PortOne 연동 실패 | 503       | `DEPENDENCY_FAILURE` |

인증 헤더 필요 여부와 오류 응답의 실제 `message`·`detail` 예시는 확인이 필요하다.

### 4.5. 회원가입용 verificationToken

| 항목            | 구현 답변 기준                                                                                  |
| --------------- | ----------------------------------------------------------------------------------------------- |
| 사용 엔드포인트 | `POST /api/v1/auth/signup`.                                                                     |
| 요청 필드명     | `verificationToken`. `SignupRequest.verificationToken`에 전달한다.                              |
| 유효기간        | 30분. `application.yml`의 `identity-verification.token-ttl: 30m`.                               |
| 사용 횟수       | 1회. `RedisIdentityVerificationStore.consume()`에서 get-and-delete로 소비하며 재사용할 수 없다. |
| 추가 검증       | 저장된 휴대폰번호·이름과 회원가입 요청값이 일치하는지 검증한다.                                 |

회원가입의 나머지 요청 필드, 성공 응답, 만료·재사용·정보 불일치 오류와 회원가입 실패 시 토큰 재발급 필요 조건은 확인이 필요하다. 위 정보만으로 전체 회원가입 DTO를 정의하지 않는다.

### 4.6. 비밀번호 규칙과 토큰 만료시간

| 항목              | 질문에서 제시한 값            | 받은 답변 및 상태                                                                                                 |
| ----------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 비밀번호          | 최소 8자, 문자 종류 3개 이상. | BE 답변은 “8자 이상, 3가지 입력값”이다. 문자 종류의 정확한 정의와 최종 정책은 확인이 필요하며 변경 가능성이 있다. |
| Access Token      | 30분.                         | 해당 만료시간에 대한 답변이 없어 확인이 필요하다.                                                                 |
| Refresh Token     | 14일.                         | 해당 만료시간에 대한 답변이 없어 확인이 필요하다.                                                                 |
| verificationToken | 만료시간 문의.                | 구현 답변 기준 30분, 1회성이다.                                                                                   |

질문에 포함된 Access·Refresh Token 만료시간을 확정값으로 취급하지 않는다.

## 5. 프로젝트

### 5.1. 상태 enum

구현 답변 기준으로 다음 5개 값이 존재한다.

```text
DRAFT
PENDING_REVIEW
ONGOING
SUCCEEDED
FAILED
```

각 상태별 수정·삭제 가능 조건, 수정 가능한 필드 및 상태 전이 규칙은 답변이 없어 확인이 필요하다.

### 5.2. 중첩 필드

| 필드           | 현재 BE 타입                      | 현재 검증                  | 남은 확인 사항                                                        |
| -------------- | --------------------------------- | -------------------------- | --------------------------------------------------------------------- |
| `introContent` | `Map<String,Object>` 자유형 JSON. | 검증 없음.                 | 내부 키와 값 타입, 필수·선택 항목.                                    |
| `disclosure`   | `Map<String,Object>` 자유형 JSON. | 검증 없음.                 | 내부 키와 값 타입, 필수·선택 항목.                                    |
| `address`      | `Map<String,Object>` 자유형 JSON. | 검증 없음.                 | 주소 구성 필드와 필수·선택 항목.                                      |
| `agreedTerms`  | `List<String>`.                   | 비어 있지 않음만 검사한다. | 약관 코드 목록과 필수 약관 구분. 코드 목록은 아직 정의되어 있지 않다. |

현재 검증이 없다는 답변은 FE·BE가 사용할 상세 스키마가 합의되었다는 의미가 아니다. 최종 JSON 스키마와 `null` 허용 여부는 별도 확인이 필요하다.

### 5.3. 이미지·영상 업로드

프로젝트 이미지·영상 업로드 API는 현재 PRD에 없어 미구현이며, BE는 구현 후 공유할 예정이다. 업로드 절차, 엔드포인트, 응답 URL 형식, 파일 크기 및 확장자 제한은 확인이 필요하다.

### 5.4. 페이지네이션

| 항목                      | 현재 계약 또는 상태                                                  |
| ------------------------- | -------------------------------------------------------------------- |
| `page`                    | 구현 답변 기준 0부터 시작한다.                                       |
| 기본 `size`               | 구현 답변 기준 20이다.                                               |
| 최대 `size`               | 현재 구현에는 제한이 없다.                                           |
| 공통 정의서의 응답 예시   | `content`, `page`, `size`, `totalElements`, `totalPages`, `hasNext`. |
| 프로젝트 목록의 실제 응답 | 위 공통 예시와 동일한 필드를 제공하는지 확인이 필요하다.             |

## 6. 구현 상태와 연동 준비

| 대상                              | 전달받은 구현 상태                                | 실제 연동을 위해 필요한 확인                         |
| --------------------------------- | ------------------------------------------------- | ---------------------------------------------------- |
| Access Token 필터·로그인 응답     | 구현 답변 있음.                                   | 환경별 배포 여부, 로그인 경로 및 전체 계약.          |
| 본인인증 재검증·verificationToken | 구현 답변 있음.                                   | Base URL, 접근 조건, 성공 상태 및 실제 응답.         |
| 회원가입                          | 토큰 소비·정보 일치 검증에 대한 구현 답변 있음.   | 전체 Request/Response와 오류 계약.                   |
| CORS·Credential 설정              | 미구현.                                           | 호출 구조, Origin, 쿠키 정책.                        |
| 회원정보 조회                     | 답변 없음.                                        | API 존재 여부 및 전체 계약.                          |
| 프로젝트 API                      | enum·중첩 필드·페이지 입력에 대한 구현 답변 있음. | 엔드포인트별 구현·배포 목록과 전체 Request/Response. |
| 프로젝트 이미지·영상 업로드       | 미구현.                                           | 구현 일정과 전체 계약.                               |

구현 답변만으로 특정 환경에서 호출 가능하다고 판단하지 않는다.

## 7. MSW 협업과 계약 변경 관리

미구현 API를 현재 명세 기준으로 FE에서 MSW 목업으로 먼저 작성해도 되는지는 답변이 없다. 정상·대표 오류 응답 예시도 엔드포인트별로 추가 공유가 필요하다.

다음 항목은 팀 합의가 필요하다.

- 최종 계약 기준을 Swagger/OpenAPI, Markdown 명세, BE DTO 중 무엇으로 할지 결정한다.
- 계약 변경 시 기준 문서 갱신 책임과 공유 채널을 결정한다.
- Swagger/OpenAPI 갱신, Markdown 수정, GitHub Issue의 역할과 변경 반영 절차를 결정한다.
- MSW 선작성 허용 범위와 임시 계약의 구분 방식을 결정한다.

이 초안은 GitHub에서 검토할 수 있는 Markdown 문서이며, GitHub 게시 자체가 위 운영 방식을 확정하지는 않는다.
