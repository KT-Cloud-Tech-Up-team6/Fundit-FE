## 적용 원칙

실제 UI, 문구, 상태, 인터랙션은 첫 번째 회원가입 Figma를 단일 기준으로 삼는다. 로그인 반응형 예시는 시각 디자인이나 문구를 가져오는 원본이 아니라, 넓은 화면에서의 콘텐츠 배치 원칙만 참고한다.

| 화면 크기       | 적용 방식                                                                                     |
| --------------- | --------------------------------------------------------------------------------------------- |
| 모바일          | 회원가입 Figma의 390px 화면을 기준으로 구현한다. 좌우 20px 여백 안에서 콘텐츠 폭은 350px이다. |
| 태블릿·데스크톱 | 인증 폼의 폭을 넓히지 않고 350px으로 유지해 화면 가운데에 배치한다.                           |
| 좁은 화면       | 폼 폭은 `min(350px, 100vw - 40px)`로 제한해 좌우 20px 여백을 보장한다.                        |

Figma 회원가입 프레임을 실측하면 상태바를 제외한 웹 콘텐츠 기준으로 헤더는 52px이고,
헤더가 있는 폼의 본문은 화면 상단에서 136px(헤더 52px + 여백 84px)에 시작한다.
가입 방식처럼 헤더가 없는 화면은 화면 상단에서 128px에 시작한다. 844px보다 낮은 화면에서도
이 상단 정렬을 유지하고, CTA는 문서 흐름 안에 두어 콘텐츠와 함께 스크롤되게 한다.

```css
.auth-content {
  width: min(350px, calc(100vw - 40px));
  margin-inline: auto;
  padding-top: 84px; /* 52px 웹 헤더 아래, 화면 상단 기준 y=136px */
}

.auth-content--without-header {
  padding-top: 128px;
}
```

## 회원가입 화면 범위

Figma `1007:9253`은 하나의 정적 화면이 아니라 아래 회원가입 플로우와 상태를 포함한다.

1. 로그인/가입 진입: FundIt 로고, 카카오·구글·이메일 로그인, 회원가입 링크
2. 약관 동의: 약관 목록 바텀시트, 항목 선택, 약관 상세 보기
3. 소셜 로그인: 외부 OAuth 완료 후 약관 동의, 이후 온보딩 이동
4. 일반 가입 및 본인인증: 디자인의 본인정보 입력 → PortOne 통합인증 → 서버 결과 검증 → 회원정보 입력
5. 상태 처리: 인증창 요청·취소·실패, 서버 검증 중·실패·완료, 입력 오류와 토스트 안내

입력과 회원가입 CTA는 기본적으로 52px 높이이며, 모바일 폼의 주요 콘텐츠 폭은 350px이다. 글꼴은 Pretendard 계열을 사용한다. 로그인 폼(`FL_C_ME_LOGIN_2`)의 "로그인" 버튼만 46px로, 회원가입 CTA와 의도적으로 다르다.

## API 연동 상태

이메일 로그인·가입, 약관 조회, PortOne 요청·서버 검증, 이메일 찾기와 비밀번호 재설정은 FE API에 연결되어 있다. 상세 요청·응답 및 인증 정책은 [API 계약](./API_CONTRACT.md), 미확정 사항은 [OPEN_DECISIONS.md](./OPEN_DECISIONS.md)를 따른다. 실제 외부 서비스 설정과 수신 검증은 별도다.

- 카카오·구글 소셜 로그인은 사업자 등록 제약으로 목업이다(2026-09-24). 버튼은 보이되 진입을 막고 OAuth 시작·콜백은 만들지 않는다. Refresh Cookie 세션 복구는 공통 인증 제공자가 담당한다.
- 일반가입 409 `ACCOUNT_ALREADY_EXISTS`(본인인증한 이름+전화번호로 기존 계정, BE PR #158)는 본인인증 토큰을 소비한 뒤라 다시 제출할 수 없다. 가입 진행 정보(토큰·본인정보·비밀번호 초안·약관)를 비우고 결과 화면 "이미 가입된 계정이 있습니다"에서 이메일 찾기(주 버튼)·로그인 화면으로 보낸다. 제출할 수 없는 가입 폼으로 돌아오지 않게 두 버튼 이동은 replace다. 헤더·브라우저 뒤로 가기는 본인인증 화면으로 가는데, 약관이 비어 있으므로 본인인증 화면은 약관 선택이 없으면(새로고침 진입 포함) 바로 가입 시작 화면(`/auth/signup`)으로 보낸다. 모바일 콜백은 약관을 먼저 복구하므로 해당하지 않는다. Figma 회원가입 `1007:9253`(플로우·IA `1007:9344` 포함)과 이메일 찾기 `FL_C_ME_IDFIND_1`~`15`에 이 상태가 없어(확인함) `FL_C_ME_IDFIND_5`의 문구 구성·텍스트 버튼 규격을 따랐다. 빈 상태 그래픽과 헤더 제목은 두지 않았고, 주 버튼은 회원가입 CTA와 같은 52px이다(#353).
- 로그인 성공은 기본 홈 또는 허용된 내부 `returnTo`로 복귀한다. `mustChangePassword`가 true이면 일반 인증 상태로 승격하지 않고 로그인 화면에서 비밀번호 변경을 먼저 진행한다. 변경 완료 후에만 회원정보를 조회하고 복귀한다. 변경을 취소하거나 화면을 벗어나면 해당 FE 세션을 비운다. FE 안내가 BE 접근 통제를 대체하지 않는다.
- 이메일 찾기는 이름·전화번호로 마스킹 주소를 조회하고, PortOne 결과를 서버 검증한 토큰으로 전체 주소를 조회한다. 모바일 콜백은 `/auth/recovery/email/callback`이며, 가입 콜백과 별도 세션에 요청 ID와 10분 만료를 보관한다.
- 재설정 요청은 계정 존재 여부에 관계없이 같은 안내를 표시한다. BE 기본·개발 메일 링크의 `/reset-password?token=…`에서 새 비밀번호를 제출하며 화면 진입 직후 URL에서 토큰을 제거해 메모리에만 유지하고, 성공 시 FE 세션을 비운다. 새로고침 시에는 메일 링크를 다시 열어야 한다. 최초 요청 URL의 서버·프록시 로그 관리는 인프라 확인 대상이다.
- Figma 로그인 섹션 `1012:11465`의 텍스트·화면정의, `interaction_spec`과 `update_history`를 확인했다. 조회된 섹션 하위 노드에는 프로토타입 연결과 주석이 없었다. 이미지 IA `1012:12137`의 과거 SMS 임시 비밀번호 설명은 현재 BE 이메일 링크 계약과 다르므로 현재 계약을 적용한다.
- BE 근거: `Fundit-backend` develop `d7ea517`의 `AuthController`, `PasswordResetService`, `PasswordChangeService`. 메일 발송기는 스텁이며 실제 메일 수신은 미검증이다.

## 확정 정책

- 본인인증의 검증 주체는 자체 SMS API가 아니라 PortOne 통합인증이다. 디자인에서 먼저 받은 이름·전화번호 등은 PortOne 요청과 최종 가입 요청에 사용한다.
- 닉네임은 필수이며 최대 50자로 제한한다.
- 비밀번호는 백엔드 기준인 8자 이상, 대문자·소문자·숫자·특수문자 중 3종 이상을 적용한다. 비밀번호 확인은 프론트에서만 검증한다.
- 가입 성공 시 발급된 세션을 유지하고 관심 카테고리 선택 화면을 거쳐 홈으로 이동한다.
- 로그인과 가입 성공 후 Refresh Cookie를 이용한 자동 로그인을 기본으로 사용한다.
- 아이디 저장은 이메일만 브라우저 로컬 저장소에 보관하며 비밀번호와 인증 토큰은 저장하지 않는다.
- 약관 목록과 전문은 `GET /api/v1/terms`를 사용한다. AI 개인화 안내와 툴팁 문구는 별도 API 필드가 생기기 전까지 프론트 문구로 관리한다.

## 세션 종료 (#254)

- 세션을 끝낼 때 `POST /api/v1/auth/logout`으로 이 기기의 Refresh Token을 서버에서 폐기한다. 로컬만 비우면 쿠키가 남아 새로고침 때 세션이 복구된다.
- 인증 헤더를 붙이지 않는다. BE는 Access Token이 만료된 뒤에도 로그아웃할 수 있게 이 경로를 열어뒀고, 쿠키가 없어도 200이다(멱등).
- Refresh 쿠키의 `Path`는 `/api/v1/auth`라 재발급과 로그아웃 두 경로에 모두 실린다. 재발급 경로로 좁히면 브라우저가 로그아웃 요청에 쿠키를 싣지 않아 서버가 폐기할 토큰을 알 수 없다.
- 로컬 무효화(토큰·세션 세대·쿼리 캐시)를 서버 응답보다 **먼저** 확정한다. 서버를 기다리면 그 사이의 refresh가 세션을 되살리고, 네트워크 장애 때 화면이 로그인 상태로 남는다.
- 쿠키를 바꾸는 요청이라 로그인·refresh와 같은 잠금으로 직렬화한다. 잠금을 기다리는 사이 새 로그인이 끝났다면 쿠키는 이미 그 세션의 것이므로 보내지 않는다.
- 서버 폐기 실패는 화면 오류로 올리지 않는다. 로컬은 이미 비로그인이고 BE 로그아웃은 멱등이다.
- 호출 지점은 로그인 중 비밀번호 변경 취소, 비밀번호 재설정 완료, 마이페이지 로그아웃 버튼이다.
- 마이페이지 진입점은 `FL_B_MY_HOME`의 `text_button_underline`(`2000:44497`)이다. 2026-09-22 12:52 `update_history`에 "[FL_B_MY_HOME] 로그아웃 버튼 추가"로 기록됐다. 문구는 "로그아웃 하기", 14px Regular·`#7A7C8A`·밑줄·높이 40px이며 메뉴 그룹 뒤 좌측 정렬이다. `TextButton`의 underline variant는 13px Medium이라 맞지 않아 같은 값을 가진 공용 클래스에 밑줄만 더했다.
- 마이페이지는 회원 전용이라 세션을 비우면 회원 게이트(`MemberAccess` → `LoginRedirect`)가 로그인 화면으로 보낸다. 로그아웃 직후 로그인을 요구하지 않도록 홈(`/` → `/live`)으로 옮긴다. **이동과 세션 정리를 같은 transition에 넣는다** — 나눠 실행하면 이 화면이 비회원 상태로 한 번 그려지면서 게이트의 로그인 이동이 홈 이동을 덮어쓴다(실제로 `/auth/login?returnTo=/my`로 갔다).
- 원본에 프로토타입 연결이 없어 이동 목적지는 확인된 디자인 지시가 아니라 이 화면의 접근 조건에서 정한 것이다.
